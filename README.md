# Intelligent-pan-tilt-facial-registrationn-system
人体跟随、两轴云台、人脸姓名与中文欢迎

从既有云台工程复制出的独立项目。人体负责位置与运动跟踪，人脸负责已登记人员的姓名标记；连续确认后，异步播放“张三，欢迎光临”。超声波和舵机控制仍由原 STM32 固件执行，G1/S1 格式保持一致。

此副本的统一入口是 **`bash run.sh`**。它打开中文控制中心，包含完整模式、人脸预览、姓名登记、语音测试、仅相机、测距监听及三路舵机验证。原项目没有被覆盖，本次没有向香橙派部署或烧录。

## 当前状态与边界

* 保留人体 NPU 推理、单人自动锁定、跨帧关联、中文 UI、实时距离、分析与显示统一旋转 180°。
* 新增 YuNet 人脸检测、SFace 姓名匹配、连续确认、未知/歧义处理，以及本地离线中文欢迎语音。
* 人体默认由 **VIPLite NPU / YOLOv5 `.nb`** 计算；人脸采用 **CPU 低频工作线程，默认最高 2 次/秒**，不是 NPU 人脸识别。
* 彩色采集默认 640×480、请求 30FPS；请求值不等于实际性能。加入人脸和语音后的板端 FPS、身份准确率和音频输出尚未验收。
* 已保留最近验收范围：水平 1100～1900μs、俯仰 1300～1600μs、前轮 1450～1550μs，回中均 1500μs。
* `calibration_confirmed=false`，前轮几何参数尚未填写，**当前默认禁止电机行进**，可做 VM 断开的视觉与云台台架联调。不要仅为启动电机而把这个值改成 true。
* HC-SR04 回波不是带身份的深度测量。随水平云台转向、目标对准、回波新鲜等条件只筛出候选距离，不能证明回波一定来自被锁定的人。

## 在香橙派首次安装

将仓库放到用户可写目录，例如 `~/FaceLock_Gimbal_Face`，然后执行：

    cd ~/FaceLock_Gimbal_Face
    bash tools/setup_orangepi.sh

脚本安装 Python 环境、中文字体、语音工具、模型和桌面图标，不安装 NPU 内核驱动，也不写 STM32。系统须有 Python 3.10～3.12、桌面环境和可用的中文语音输出设备；NPU 须满足[环境配置](docs/01_安装与环境.md)的实际硬件与 SDK 条件。

## 登记与欢迎

1. 执行 `bash run.sh` 或点击桌面“人脸欢迎与云台控制中心”。
2. 点“测试中文欢迎语音”，确认扬声器能听到声音。
3. 点“登记人脸姓名”，输入姓名，只让该人员一张清楚正脸入镜，采满 8 个样本。
4. 关闭登记窗口，再点“人体＋人脸姓名＋语音预览”。连续确认后显示姓名并欢迎；陌生人显示“未登记”。
5. 预览通过后，VM 断开，选择“完整视觉＋人脸姓名＋语音＋云台＋测距”。

也可以用命令：

    bash run.sh --mode enroll --name '张三'
    bash run.sh --mode preview
    bash run.sh --mode full
    # 明确只跟随某个已登记人脸ID；身份不新鲜/歧义时发无效控制。
    bash run.sh --mode full --follow-face 1

默认模式按人体规则跟随，并给已知人标姓名/欢迎；不要求每次都看见正脸。`--follow-face` 模式要求身份持续有效，转身较久就会暂停有效转向。两种行为见[姓名与语音说明](docs/03_人脸姓名与语音.md)。

    git clone 你的仓库地址 FaceLock_Gimbal_Face

不用Git也可以下载并解压仓库ZIP，将展开后的仓库放到 `~/FaceLock_Gimbal_Face`。应直接看见 `README.md`、`run.sh`、`app/`、`firmware/`、`tools/`，而不是在多层压缩目录里找入口。

记录本次使用的提交号；下载ZIP时记录发布版本和下载时间。不同人不能只说“我用最新版”，却使用不同副本。

### 1.2 校验

    cd ~/FaceLock_Gimbal_Face
    python3 tools/verify_files.py
    python3 tools/audit_package.py

预期：源码清单不一致数为0，审计 `errors` 为 `[]`。此时没有模型也可检查源码与HEX。

正式HEX为：

校验只证明文件一致，不证明实物安全或功能正确。自己改过源码/配置后，清单不符可能是预期结果；保留变更记录，不要为“变成0”把自己的有效修改抹掉。

**本阶段完成：** 文件结构正确，已记录提交/版本，源码/HEX校验通过。

## 阶段1：核对系统，先把环境装完整

### 2.1 读取实机信息

    cat /proc/device-tree/model
    uname -a
    uname -m
    cat /etc/os-release
    python3 --version
    ls -l /dev/video0
    ls -l /dev/serial/by-id/

没有TTL时 `by-id` 目录不存在可以先做视觉；没有 `/dev/video0` 则先解决摄像头枚举，不进入识别测试。记录实际输出，不根据外壳、商品标题或历史称呼推断SoC。

从VNC桌面打开终端再启动GUI。仅通过普通SSH会话启动窗口可能缺少正确显示会话；不要随意强制 `DISPLAY=:0` 掩盖权限/会话问题。

### 2.2 联网安装

    cd ~/FaceLock_Gimbal_Face
    bash tools/setup_orangepi.sh

以日常桌面用户运行，**不要sudo整个脚本**。脚本内部按需调用sudo安装依赖，创建 `app/.venv`，安装固定Python包、模型和桌面入口；不会安装NPU内核驱动，不会烧录STM32。

当前固定依赖：Python3.10～3.12、numpy1.26.4、OpenCV4.10.0.84、pyserial3.5、Pillow11.3.0。实际镜像/架构若没有对应安装包，记录pip错误并解决依赖兼容，不用随意混装多个OpenCV版本“碰碰运气”。

### 2.3 安装中途失败怎么办

脚本使用遇错退出模式。**中途退出不表示后面的组权限、NPU编译和桌面入口已经执行。** 按终端最后一条错误处理后重跑同一脚本。

| 失败位置 | 处理  |
| --- | --- |
| apt更新/安装 | 检查镜像网络、软件源、包名称及权限；先让系统依赖安装完成 |
| Python版本断言 | 使用兼容Python/镜像；这不是人脸模型错误 |
| pip安装 | 核对Python版本、架构、网络与实际错误；始终使用仓库`.venv` |
| 模型下载 | 用下一节离线方法恢复，之后重跑安装脚本 |
| NPU桥接编译 | 核对官方头文件/库/SDK；若只先验证CPU，可按下面的手动收尾方法，不伪造`.so` |
| 桌面图标 | 确认虚拟环境存在，手动运行 `bash tools/install_desktop.sh` |

若NPU桥接失败但只准备先完成CPU功能验证，确认apt/Python/模型都已安装后，可完成以下收尾；这不会修好NPU：

    sudo usermod -aG video,dialout,audio "$(id -un)"
    bash tools/install_desktop.sh

设备组权限变更后注销桌面并重新登录，再连接VNC；不是只关闭一个终端。

### 2.4 离线恢复模型

模型文件不在GitHub上传包内；提供者可合法提供已校验的离线副本，或复现者自行联网获取。

    app/.venv/bin/python tools/models.py
    # 或：把占位路径换成真实离线目录，不能照抄中文占位路径。
    app/.venv/bin/python tools/models.py --offline /你的模型目录
    app/.venv/bin/python tools/models.py --verify

需要的三个ONNX：

| 文件  | 用途  | 是否必须 |
| --- | --- | --- |
| `face_detection_yunet_2023mar.onnx` | 人脸检测 | 姓名/欢迎模式需要 |
| `face_recognition_sface_2021dec.onnx` | 人脸特征识别 | 姓名/欢迎模式需要 |
| `object_detection_nanodet_2022nov.onnx` | CPU人体检测 | CPU路线和完整软件回归需要 |

SHA256及许可证见[安装与环境](01_安装与环境.md)。工具匹配SHA后才接受文件，不使用网页HTML或Git LFS指针代替模型。

### 2.5 复现软件回归

    cd ~/FaceLock_Gimbal_Face/app
    .venv/bin/python -m unittest discover -s tests -v
    cd ..
    app/.venv/bin/python tools/test_firmware.py

当前发布基线：190项Python测试和4组C原生测试通过。测试数量以下载版本为准；后续增加测试不能仍机械要求“必须恰好190”。C测试在临时目录编译、执行，不烧录、不写正式HEX。

**本阶段完成：** 兼容环境与三个模型可用，软件测试通过，桌面/设备组设置生效。

## 阶段2：先独立验证摄像头和声音

### 3.1 摄像头

    cd ~/FaceLock_Gimbal_Face
    v4l2-ctl --list-devices
    v4l2-ctl -d /dev/video0 --list-formats-ext
    fuser /dev/video0
    bash run.sh --mode camera

检查彩色、清晰度、亮度和采集FPS，确认人物能完整入镜。设备占用时先正常关闭原程序，不随意结束不明进程。请求30FPS不等于相机实际交付30FPS，光线不足时自动曝光可能降低有效采集速度。

**注意方向：** 当前“仅相机”工具用于原始采集检查；它没有像完整视觉入口那样显式指定180°旋转。人体/人脸预览默认在分析前旋转180°，不能仅凭两个窗口朝向不同判定推理错位。正式跟随必须确认“用于分析的帧”和“输出画面”方向一致。

### 3.2 中文语音

    aplay -l
    espeak-ng --voices=cmn
    bash run.sh --mode speech-test --name '张三'

人耳确实听到“张三，欢迎光临”才算通过。终端显示“已欢迎”只说明外部合成命令未报错，不证明扬声器出声。

VNC能看到画面不代表它会把算力板的声音转到电脑。先让板端的音箱正常出声；若有多块声卡，用系统声音设置选择默认输出并取消静音，不在不知道声卡编号时硬编码某个设备。

**本阶段完成：** 可用彩色图像、真实采集FPS有记录，扬声器实际出声。

## 阶段3：CPU路线验证人体、姓名和欢迎

本阶段不连接串口，不驱动舵机/电机。没有NPU也能先验证软件功能，但不保证达到项目目标帧率。

### 4.1 仅人体基线

    bash run.sh --mode body-only --backend cpu

保持头到腰至少完整入镜、正面照明，先静止再缓慢左右移动。检查人体框、自动/手动选择、Q退出。单人01是当前槽位，不能解释为“识别出同一个人的永久身份”。

### 4.2 登记姓名

关闭前一个相机窗口，然后：

    bash run.sh --mode enroll --name '张三'
    bash run.sh --mode list

只让待登记者一张清楚正脸入镜，程序收集8个合格样本。先正脸再缓慢小幅转头，不用大幅摇头；超时或Q取消不写库。相同显示名再次登记会追加到同一身份，两个同名人员应使用可区分名字。

特征库为 `app/data/named_faces.json`，这是个人数据，不上传GitHub；默认不存登记照片。姓名库变化后重新启动视觉，不期望运行中的程序自动加载新名单。

### 4.3名标记与欢迎

    bash run.sh --mode preview --backend cpu

检查：

1. 正脸清楚，连续三次确认且跨至少0.5秒后显示姓名，并实际听到欢迎。
2. 持续站在画面里不反复播报。
3. 短暂转头/遮挡后恢复，不频繁重复欢迎。
4. 未登记人员不播报确定姓名；多人交叉或歧义时不乱报。
5. 至少离开已确认姓名状态8秒且距上次欢迎至少60秒，才允许再次欢迎；转身长时间看不见脸也可能算“姓名离场”。

人脸CPU异步默认最高2Hz，不等于人体帧率。音频失败显示错误，普通标签模式仍继续人体处理。该实现没有活体检测，照片/屏幕可能被当人脸，不能当作安全身份认证。

**本阶段完成：** 视觉标签、本人登记、未知者处理、欢迎去重都经过真人观察。记录实际误认/漏认，而不是仅说“模型加载成功”。

## 阶段4：具备条件后验证NPU路线

### 5.1 检查官方环境

    app/.venv/bin/python app/tools/check_npu.py
    ls -l /dev/vipcore
    ls -l /usr/include/vip_lite.h
    ls -l /opt/yolov5/model/yolov5.nb
    sha256sum /opt/yolov5/model/yolov5.nb

清单工具只是盘点，不是已成功使用NPU。缺少设备节点不一定证明芯片没有NPU，但没有可用驱动/运行库时程序确实不能直接推理。按实际SoC安装官方兼容镜像/SDK，不能混用别的板卡驱动。

官方SDK/模型不齐时停在此阶段，前面CPU验证仍有价值。**本文没有一条经过验证、能把任意YOLO权重转成当前板卡模型的通用转换命令。** 不要把YOLO新版本ONNX改后缀为`.nb`。

### 5.2 核对模型接口

现有适配器固定640输入与YOLOv5三尺度输出，支持源码明确检查的两种输入布局：

* CHW uint8量化输入 `(1,3,640,640)`，zero point为0、scale约为1/255；输出为 `(1,3,80,80,85)`、`(1,3,40,40,85)`、`(1,3,20,20,85)`。
* RGB图像uint8输入 `(1,640,640,3)`；对应输出布局为 `(1,3,85,80,80)`、`(1,3,85,40,40)`、`(1,3,85,20,20)`。

布局只是必要条件，还必须核对类别顺序（当前解码以person为0）、anchors、量化、预处理和导出语义。维数碰巧相同不代表任意模型可替换。模型不匹配时应换成经过核对的模型或修改并验证解码，不删除校验后继续跑。

### 5.3 本机编译桥接

    cd ~/FaceLock_Gimbal_Face/app/native
    bash build.sh
    ldd libfacelock_vip.so
    cd ../..

检查链接库没有 `not found`。`.so`在目标板编译，不复制另一CPU架构的二进制；编译成功仍需真实模型推理验证。

### 5.4 真正运行模型

准备一张经本人同意、人体清楚的本地测试图，路径不要指向并不存在的文件：

    app/.venv/bin/python app/tools/benchmark_npu.py \
      --image /你的本地人体测试图.jpg \
      --frames 100 --require-person
    bash run.sh --mode preview --backend npu

记录模型SHA、推理结果和耗时；`--require-person`要求静态测试图确实检出人体。静态推理FPS不能当作摄像头＋识别＋UI＋通信的FPS。

注意：当前辅助benchmark含“精简结果与完整解码参考比对”。若实际模型采用上述RGB图像输出布局，辅助完整解码路径未必支持该布局。出现该处布局错误时，先区分是benchmark参考比对限制还是主适配器推理失败；不能据此直接宣布NPU故障，也不能跳过结果正确性验收。应由算法同学核对匹配的测试路径后记录。

当前正式入口内部默认NPU模型路径为 `/opt/yolov5/model/yolov5.nb`；启动器没有通用 `--model` 参数。另一个路径通过静态benchmark的 `--model` 可单独测，但要用于正式入口，须由算法同学明确调整模型路径并记录源码变更。

**本阶段完成：** 同一合法模型与SDK可真实推理，完整人脸预览能运行，结果/模型哈希有记录。尚不等于20FPS通过。

## 阶段5：主控烧录和接线核对

### 6.1 固件与工具

* Keil打开 `firmware/Project_VEHICLE.uvprojx`，目标为 `FaceLock_GIMBAL_20261104`。
* 使用原ARM Compiler 5配置，缺少工具链/STM32F1设备包时先安装匹配环境。
* 可直接烧录同包 `firmware/Objects/FaceLock_GIMBAL.hex`，或者正确编译后烧录自己的输出；自己重编生成的HEX应单独记录哈希，不能仍假称等于打包HEX。
* 使用ST-Link/SWD，不是TTL下载。已有同版本主控无需仅因新增人脸/语音再次烧录。
* CubeMX的IOC仅用于引脚查看，不要Generate Code覆盖标准外设库工程。

首次Download后须看到实际烧录/校验成功，再给主控正常复位/运行。不要把“Keil窗口打开”当作“固件已写入”。

### 6.2 接线表

断电接线；三路均按实物信号线/供电线确认，不只凭线色。下表与源码对应：

| STM32 | 接外部器件 | 作用  |
| --- | --- | --- |
| PA0 | 水平舵机信号 | TIM2_CH1 |
| PA1 | 前轮舵机信号 | TIM2_CH2 |
| PA2 | 俯仰舵机信号 | TIM2_CH3 |
| PA9 TX | TTL RX | 主控向板端回传 |
| PA10 RX | TTL TX | 板端向主控下发 |
| GND | TTL/舵机电源/传感器/驱动的公共地 | 共同电平参考 |
| PB6 | HC-SR04 TRIG | 触发测距 |
| PB7 | 经核对电平接口后的ECHO | TIM4_CH2输入捕获 |
| PB8 / PB9 | OLED SCL / SDA | 原OLED接口 |
| PA13 / PA14 | ST-Link SWDIO / SWCLK | 调试与烧录 |
| PA6 / PA7 | TB6612 PWMA / PWMB | 电机PWM，整车阶段使用 |
| PB12 / PB13 | AIN1 / AIN2 | A路方向 |
| PB14 / PB15 | BIN1 / BIN2 | B路方向 |
| PB10 | STBY | 驱动待机控制 |

接线参考在 `assets/wiring/`。HC-SR04与摄像头一起左右转，但不随俯仰上下转。ECHO电平方案由电控核对，不能把“分压下端接地”误解成把ECHO信号直接短接到GND。

当前项目没有替你完成新硬件的电源容量设计。三只SG90同时启动的供电、面包板压降和公共地必须现场检查；ST-Link、TTL、外置电源的供电正极不随意并联。**下述台架阶段电机VM保持断开。**

**本阶段完成：** HEX/编译版本可追溯、SWD烧录成功、针脚和电源逐项核对。

## 阶段6：先验收独立串口、距离和三路舵机

### 7.1 串口枚举与监听

    ls -l /dev/serial/by-id/
    ls -l /dev/ttyUSB* /dev/ttyACM*
    bash run.sh --mode distance

入口自动选唯一串口；有多个设备时明确指定经核对的设备路径：

    bash run.sh --mode distance --port /dev/ttyUSB0

115200、8N1、3.3V逻辑、TX/RX交叉、GND共地。默认监听10秒，仅收数据不发控制。预期看到 `#D1` 等主控遥测；监听只能证明接收路径，不单独证明板端TX已正确到达主控。

| 观察  | 解释  | 下一步 |
| --- | --- | --- |
| 完全无遥测 | 可能端口、供电、TX/RX、GND、固件/运行状态或权限问题 | 先修基础链路，不改识别模型 |
| 有D1但valid为0 | 主控已回传，回波链路未通过 | 查TRIG/ECHO、电平接口、朝向和被测物 |
| D1距离稳定有效 | 距离采集和主控→板端链路有证据 | 继续单轴验证，再验证双向指令 |

超声波先对平整目标，不先对柔软/倾斜衣服判定模块损坏。用尺子布置30cm、35cm、50cm、100cm等位置，记录实际误差，本文不虚构误差指标。

### 7.2 分别测试舵机

关闭监听后逐个执行：

    bash run.sh --mode pan
    bash run.sh --mode tilt
    bash run.sh --mode front

各入口默认回中1500μs、再1450/1550μs小幅验证，首次要求两侧机械自由；不是一开始就跑完整1100～1900范围。固定并支撑云台，先单只/小幅，确认没有卡住嗡响，再做带载测试。

观察的是**以1500μs中位为基准的两个最终停留位置**，不是只看每次运动方向。两个位置应位于中位两侧，停留稳定，最后回中。

台架测试收到G2后才继续有效指令，全程 `motion=0`。主控回传PWM正确只能证明软件输出，真实轴不动时仍查供电、地、信号、舵机和机构。不要仅加大控制增益。

### 7.3 新硬件重新标定方向/范围

当前副本方向参数均为-1，原机构验收范围为：

| 轴   | 当前运行范围 | 回中  |
| --- | --- | --- |
| 水平  | 1100～1900μs | 1500μs |
| 俯仰  | 1300～1600μs | 1500μs |
| 前轮  | 1450～1550μs | 1500μs |

这些是原机构的结果，**不能保证另一套舵盘/支架直接适用**。新机构先让1500μs对应镜头基本朝前/水平，逐级确认方向和安全限位。参数在 `app/gimbal_config.json` 与 `app/steering_gimbal_config.json`；前轮运行范围由后者决定。只改与实测不符的轴，记录变更。

固件解析器允许的水平1000～2000、俯仰1300～1700比运行配置宽，不是扩大机械范围的授权或验收依据。

**本阶段完成：** D1有效、三路两侧/回中实际通过、方向和限位记录明确。

## 阶段7：VM断开的完整视觉云台联调

### 8.1 启动

关闭所有旧相机/串口程序，固定车架，头到腰入镜：

    bash run.sh --mode full
    # 只有CPU条件时，可先验证功能链路，不以此验收NPU性能。
    bash run.sh --mode full --backend cpu

完整模式启用串口；`preview` 和 `body-only` 不连接串口。需要测舵机时不能一直运行仅预览后问“为什么不转”。窗口应有中文人体/姓名标记、处理FPS、相机FPS、相对车体角度、超声波距离和通信状态。

### 8.2 按顺序观察

1. 人物居中静止约10秒：锁定稳定，水平云台不持续往复抖动。
2. 缓慢左右各移动并停留：镜头朝人物所在方向修正，前轮按实际安装方向同侧转向。
3. 缓慢降低身体再站直：俯仰调整有助于保留上半身，无卡住/持续嗡响。
4. 接近画面边缘：记录是否碰软件限位。碰限位时继续加增益不能增加物理行程。
5. 离开画面超过3秒：健康通信持续无效控制时，观察保持后回中；重新入镜重新确认。
6. 停止程序/断开串口：验证主控断链保护。断链约500ms开始回中，不能误要求它同样保持3秒。
7. 查看D1、M1、G2是否持续刷新；测距不是仅在窗口保留上次数字。

### 8.3 人脸默认行为与指定身份行为

    # 默认：按人体规则跟随；已登记的人额外标姓名并欢迎。
    bash run.sh --mode full
    # 先查看登记名单，再选择真实存在的身份ID。
    bash run.sh --mode list
    bash run.sh --mode full --follow-face 1

默认标签模式会跟随符合人体选择规则的陌生人；不是“只追登记的人”。指定身份模式才会在姓名未知/过期/歧义时撤销有效控制，较久转身可能暂停跟随，这是保守设计。

**本阶段完成：** 方向、居中、上半身构图、失踪/断链保护、姓名和距离显示均实际观察通过。

## 阶段8：性能、准确率与稳定性验收

### 9.1 同场对比

固定相机/底座、照明、人物距离与动作，关闭其他重负载应用，每轮分别60秒，前一个退出后再启动下一个：

    # 下列默认NPU；CPU实验需在每条命令加 --backend cpu，并分别记录。
    bash run.sh --mode body-only --max-seconds 60 --metrics-json logs/body_baseline.json
    bash run.sh --mode preview --max-seconds 60 --metrics-json logs/face_welcome.json
    bash run.sh --mode preview --face-hz 1 --max-seconds 60 --metrics-json logs/face_1hz.json
    # 先确认VM断开，再测通信和云台参与时的完整链路。
    bash run.sh --mode full --max-seconds 60 --metrics-json logs/full_gimbal.json

指标路径相对 `app/`，结果实际写在 `app/logs/`。仅预览无G2姿态反馈，云台不会动作；它与完整闭环不是完全同一条件，所以两者都要记录。

| 指标  | 用途  |
| --- | --- |
| `steady_wall_fps` | 经过预热后的实际处理吞吐，核心FPS指标 |
| `observed_capture_fps` | 观察到的采集速度，与处理FPS区分 |
| `host_frame_age_p95_ms` | 大部分帧到控制时的年龄，反映滞后风险 |
| `stages` | 检测/前处理/NPU复制/后处理/UI等耗时分解 |
| `valid_percent`、`longest_valid_seconds` | 跟随有效性，不是人脸准确率 |
| `face.completed`、`face.last_ms`、`face.error` | 人脸实际批次、最近耗时及错误 |
| `serial_error`、`gimbal`、`single_person` | 链路、控制门槛和槽位状态 |

完整UI有意采用960×660画布，中间视频640×480。把整个窗口缩小不代表NPU640×640输入变小；不能把减少UI像素直接等同模型推理加速。

目标可以记录为“彩色640×480、实际处理≥20FPS”，但**本副本尚未实测达标**。原现场记录也没有证明稳定20FPS。若不达标，按相机→NPU→CPU人脸/匹配→UI→系统竞争顺序查耗时，不使用黑图、空场或重复旧帧刷数字。

### 9.2 真人身份与跟随测试表

至少覆盖已登记本人、未登记人员、两人同框/交叉、短遮挡、离开再进入、衣着相似、转身及弱光。每项重复次数由团队预先填写，再统计：

| --- | --- | --- | --- | --- | --- | --- | --- |
| 登记本人正面 | 待填  |     |     |     |     |     |     |
| 未登记人入镜 | 待填  |     |     |     |     |     |     |
| 两人同框/交叉 | 待填  |     |     |     |     |     |     |
| 短时遮挡/转头 | 待填  |     |     |     |     |     |     |

### 9.3 延长稳定性

建议先连续10分钟，再安排30分钟多人/转头/语音与云台联合测试。时间是建议测试计划，不是已经完成的证据。记录USB重连、进程退出、串口超时、语音错误、温度/降频和供电异常；遇到异常保留日志再定位。

## 阶段9：可选的电机和整车复现

此阶段超出“仅云台迎宾”的最小目标，必须由电控/机械同学共同参加。

### 10.1 先完成测量与标定

| 参数/项目 | 目的  | 当前状态 |
| --- | --- | --- |
| 相机内参/视场、畸变、旋转后的坐标约定 | 像素误差转换角度 | 当前参数不能当作任意相机实测值 |
| 云台PWM→实际角度与方向 | 估计光轴相对车身朝向 | 当前10μs/°为沿用估计，需实测 |
| `wheelbase_m` | 转弯几何 | null |
| `front_us_per_wheel_degree` | 期望前轮角转换PWM | null |
| 相机/超声波相对车体偏移 | 测距/方位坐标一致 | 默认值需按实物核对 |
| 机械范围和动力电源 | 防止错误动作/供电失效 | 新硬件逐项验收 |

相关配置位于 `app/gimbal_config.json` 和 `app/steering_gimbal_config.json`。可参考已有 `app/tools/calibrate_camera.py`，但棋盘格内角点数、方格尺寸、照片分辨率/焦距和旋转状态都必须使用真实值。工具输出只是标定结果，仍需独立角度验证。

**不要只把 `calibration_confirmed` 改为true来绕过停车。** 只有完成全部实测并审阅配置，才将该状态作为验收结果写入。

### 10.2 架空验证

固定并架空车轮，按电机额定电压接通VM。先短时、后连续，确认方向、缓升和停车：

* 正常视觉＋对准＋新鲜有效距离满足门槛，才允许行进。
* 距离≤300mm停车；不是“只有恰好300mm才停车”。
* 距离≥350mm并满足恢复条件才重新允许启动，保留迟滞，避免临界值来回启停。
* 距离失效/超时、视觉无效、串口断开均停车。
* 目标电机PWM约30%，约1秒缓升；没有编码器，不能保证不同电池/负载下实测速度恒定。
* 多人、云台未稳定/未对准、过旧回波或未标定时不放行。

不要为了看到电机转而伪造D1、视觉有效位或motion许可。先判断门槛中哪项未满足，再处理对应硬件/标定。

### 10.3 低速场地与距离含义

架空全部通过后，再到有足够空间、有人可断电的场地低速测试。注意HC-SR04只给声束回波，不能识别回波属于哪一个人；即使与云台光轴一致，也可能被前方障碍物截获。UI“对准回波候选”不等于经过身份验证的人体距离。

如需求升级为可靠区分目标人体与障碍物的距离，需要另行评估深度/距离传感器、融合与障碍物处理；不是调一个超声波阈值就能保证。

**本阶段完成：** 电控和算法共同记录实际电机、距离停车、故障停车及实车转向结果，完成标定和版本归档。

## 常见失败的定位顺序

| 问题  | 第一证据 | 应先做什么 |
| --- | --- | --- |
| 下载后不能运行NPU | SoC/SDK盘点、缺失模型/库报错 | 先走CPU功能路线，补官方SDK与匹配模型 |
| 安装完没有图标 | 安装日志是否中断 | 修错误后重跑；或环境完整时单独装图标 |
| SSH能连但窗口不开 | GUI会话/终端错误 | 从VNC桌面终端启动，核对显示会话 |
| 画面黑/过曝/低FPS | 原始相机预览、照明、采集FPS | 默认自动曝光，恢复可用画质后再调固定曝光 |
| 模型快但跟随慢 | 真实处理FPS、p95年龄、系统负载 | 看全管线，不看静态模型峰值 |
| 姓名一直“确认中” | 脸大小/清晰度、脸批次耗时、持续人体检测 | 改照明/取景，检查人脸结果是否过期，不盲降阈值 |
| 标签正确但没声音 | 独立语音测试和声音输出 | 检查板端声卡/音箱/VNC音频区别 |
| 舵机无动作 | 当前是否full、A1/G2、单轴实际动作 | 先确认启动模式，再定位协议/供电/机构 |
| 一侧跟随不足 | 方向、命令值、软件限位、机械余量 | 区分限位与增益，分阶段验证，不能直接扩大到机械极限 |
| UI有旧距离 | D1年龄/有效位和串口接收 | 核对实时刷新，不能把缓存数字当新测量 |
| 马达不转 | motion、标定状态、M1、距离/视觉门槛和VM | 当前默认禁止行进；按阶段9处理 |
| 程序占用设备 | 会话锁、`fuser`、旧窗口 | 正常退出旧进程，避免开多个视觉程序 |

日志位于 `app/logs/session_*.log` 和控制/遥测CSV。最小收集命令：

    ls -lt app/logs/
    # 将文件名换成这一次实际运行生成的日志。
    tail -n 120 app/logs/你的本次日志.log

回报问题时提供版本、系统、启动命令、最后错误和复现动作，不只发一张窗口截图。公开视频/日志前先去掉真人姓名、图片和私人网络信息。
